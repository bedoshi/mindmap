# 方針・設計の決定記録

このプロジェクトで決めた方針と、その経緯・理由を時系列で記録する。新しい決定を追加するときは末尾に追記し、既存の決定を覆す場合は元の項目に「→ 変更」と追記したうえで新しい項目を書く。

## 2026-11-07

### D-01 MindMeister 風のマインドマップアプリを作る

- **決定**: MindMeister のような操作感（中心トピックから左右に枝を伸ばす自動レイアウト、Tab / Enter によるノード追加、ドラッグでの付け替え）を目標にする。
- **経緯**: 最初の要望が「mindmeister のような mindmap アプリを作りたい」であったため。
- **影響**: ノードの手動配置は行わず、常に自動レイアウトにする。

### D-02 追加の実行時依存パッケージを入れず、React + SVG で描画する

- **決定**: 状態管理ライブラリや描画ライブラリ（React Flow、D3 など）は使わず、React と標準の DOM / SVG だけで実装する。→ 変更: 実行時依存は D-16 で `electron-updater` が加わった（Electron のメインプロセス専用。レンダラーは React のみ）。
- **理由**: ツリー構造の自動レイアウトとベジェ曲線の描画だけなら自前実装で十分であり、依存を増やさない方が保守しやすい。
- **影響**: レイアウト計算（`src/model/layout.ts`）とツリー操作（`src/model/mindmap.ts`）は純粋関数として持つ。

### D-03 Web 版を残しつつ Electron 版も提供する

- **決定**: ブラウザで動く Web 版はそのまま残し、同じコードを Electron で包んだデスクトップ版を追加する。
- **経緯**: 「Electron で動くアプリとして実装することは可能か」という質問に対し、可能である旨と構成案を提示し、「Web 版も残しつつ Electron アプリも作る」方針が選ばれた。
- **影響**: `index.html` と `src/` を両者で共有し、Electron 固有のコードは `electron/` に隔離する。保存先の違いは `MapStorage` インターフェースで吸収する。

### D-04 保存先は OS の慣習に沿ったユーザーデータディレクトリにする

- **決定**:
  - Windows: `%LOCALAPPDATA%\mindmap`
  - macOS: `~/Library/Application Support/mindmap`
  - Linux: `$XDG_DATA_HOME/mindmap`（未設定なら `~/.local/share/mindmap`）
- **経緯**: 当初の案は「Windows は `AppData\LocalLow`、macOS / Linux は `~/.cache/mindmap`」だった。これに対して次の懸念を伝えた。
  - `LocalLow` は低権限プロセス用の場所で、一般的なアプリは `AppData\Local` を使う。
  - `~/.cache` は「消えても困らないキャッシュ」を置く慣習の場所で、クリーンアップツールに削除される可能性がある。永続データには `~/.local/share` や `~/Library/Application Support` が慣習に沿う。
  - 検討の結果、「OS の慣習に沿った場所」に変更することになった。
- **補足**: Electron の `app.getPath('userData')` は Windows で Roaming（`%APPDATA%`）を返すため使わず、自前で解決している。検証用に環境変数 `MINDMAP_DATA_DIR` で上書きできる。

### D-05 マップごとに 1 ファイルとし、複数マップを扱えるようにする

- **決定**: 1 マップ = 1 ファイル（`maps/<UUID>.xml`）。アプリ内にマップ一覧を持ち、作成・切り替え・削除ができる。
- **経緯**: 「1 ファイル固定か、マップごとに 1 ファイルで複数マップを扱うか」の確認に対し、後者が選ばれた。
- **影響**: Web 版も同じモデルに合わせ、localStorage にマップごとのキーで保存する。マップのタイトルはルートノードのテキストとし、別途の名前付け機能は持たない。

### D-06 自動保存を基本とし、Ctrl+S で明示的にも保存できるようにする

- **決定**: 変更から約 0.6 秒後に自動保存する。`Ctrl+S` と「保存」ボタンで即時保存できる。ツールバーに保存状態を表示する。
- **経緯**: 「自動保存か明示的な保存か」の確認に対し、「自動保存としつつ Ctrl+S でも保存できるように」という回答だった。
- **影響**: ウィンドウを閉じるときにも保留中の変更を書き出す。マップの切り替え・削除の前にも必ず書き出す。

### D-07 保存形式は XML を正規とし、JSON 形式は廃止する

- **決定**: ファイル保存・書き出し・読み込み・localStorage のすべてで同じ XML 形式を使う。最初の試作で使っていた JSON 形式は廃止し、移行処理も入れない。
- **経緯**: XML での保存が要望に含まれていた。形式を 1 つにして実装と仕様を単純にするため JSON は廃止した。JSON 形式のデータは当日の試作データしか存在しなかったため、移行は不要と判断した。
- **影響**: XML の生成・解釈はレンダラー側で行い（ブラウザ標準の `DOMParser` を使う）、Electron のメインプロセスはファイルの読み書きだけを担当する。形式の詳細は [spec.md](./spec.md#xml-形式) を参照。

### D-08 Electron のビルドには electron-vite を使う

- **決定**: `electron-vite` でメイン / preload / レンダラーをビルドし、インストーラは `electron-builder` で作る。
- **理由**: 既存の Vite 構成をほぼそのまま流用でき、開発時に HMR 付きで Electron ウィンドウを起動できる。
- **補足**: `package.json` が `"type": "module"` のため preload は ESM（`.mjs`）で出力され、Electron の制約により `sandbox: false` にしている（`contextIsolation` は有効）。`npm run package` によるインストーラ作成はまだ動作確認していない。

### D-09 Lint は oxlint、テストランナーは未導入

- **決定**: Lint は ESLint ではなく oxlint を使う（スキャフォルディング時の選択を踏襲）。単体テストはまだ導入していない。→ 変更: テストランナーは D-12 で Vitest を導入した。
- **補足**: 後から追加された汎用スキル `react-ts-test-lint-rules` は Vitest / ESLint / Prettier を前提にしている。導入する場合は依存パッケージの追加になるため、独立したコミットで行う（CLAUDE.md のコミットルール参照）。

### D-10 汎用の React + TypeScript 規約スキルと既存構成の差分は未解決

- **状況**: 機能実装のあとに `react-ts-structure-naming-rules` / `react-ts-component-design-rules` / `react-ts-test-lint-rules` が追加された。各スキルは「プロジェクトに既存の規約がある場合はそちらを優先し、差分があれば指摘する」としているため、既存構成はそのままにしている。
- **差分**:
  - ファイル名がパスカルケース（スキルはケバブケース）
  - `features/` 単位ではなく `model` / `storage` / `hooks` / `components` の種類単位の構成
  - `src/storage/index.ts` が barrel ファイル、`App.tsx` が default export
  - `@/` パスエイリアス未設定、ESLint ではなく oxlint
- **今後**: 規約に合わせて構成を移行するかどうかは未決定。移行する場合は機能変更と分けた独立のタスク・コミットで行う。

### D-11 ドキュメントの置き場所

- **決定**: 機能仕様は `docs/spec.md`、方針決定の経緯はこの `docs/decisions.md`、実装構成は `.claude/skills/mindmap-app-architecture/SKILL.md`、コマンドは `.claude/skills/mindmap-app-commands/SKILL.md` に書く。`readme.md` は概要と各ドキュメントへのリンクに留める。
- **経緯**: 「ここまでのやり取りの情報を CLAUDE.md または仕様面については docs 配下にまとめてほしい」という要望による。それまでは `readme.md` に仕様を書いていた。

### D-12 単体テストに Vitest + Testing Library を導入する

- **決定**: テストランナーは Vitest（4 系）、DOM 環境は jsdom、コンポーネントテストは Testing Library（react / user-event / jest-dom）。テストファイルは対象と同じディレクトリに `対象名.test.ts(x)` で置く。
- **経緯**: 「unit test code を追加したい」という要望による。`react-ts-test-lint-rules` スキルの前提に合わせた。
- **スキルとの差分**:
  - HTTP 通信が無いため MSW は導入しない。
  - Lint は oxlint のまま（D-09）。ESLint / Prettier への移行は D-10 の構成移行と合わせて判断する。
  - カバレッジの閾値は設定しない（数値を満たすためのテストを書かないため）。
  - Vitest は npm の依存解決で 4.1 系が入った（最新は 5 系）。4 系は Vite 8 に対応しており、スキルの前提とも一致するためそのまま使う。
- **影響**: `src/test/setup.ts` で jsdom に無い API（Pointer Capture、Canvas の getContext）と Node 側の localStorage を補っている。Electron のメインプロセス本体はテスト対象外とし、ファイル入出力だけを Node 環境で検証する。

### D-13 リリースは GitHub Actions で Windows 版インストーラを GitHub Releases に公開する

- **決定**: `v*` タグの push をきっかけに `.github/workflows/release.yml` が Windows 上でビルドし、`gh release create` で NSIS インストーラ（`.exe`）・`.blockmap`・`latest.yml` を Release に添付する。電子署名と自動アップデートは扱わない。
- **経緯**: 「リポジトリ上でリリースを作成し、electron の .exe ファイル等をダウンロードできる形にしたい」という要望による。手元の exe を手動アップロードする方法と比べ、再現性のある環境でビルドできるためワークフローを選んだ。
- **補足**: 対象は Windows のみ（macOS / Linux は未検証）。ワークフローは公開前に lint・型チェック・テストを通す。`electron-builder` の自動公開は `--publish never` で止め、公開は `gh release create` に一本化している。

### D-14 ノード削除後の選択先は「上の兄弟 → 下の兄弟 → 親」の順にする

- **決定**: ノードを削除したあとに選択するノードは、直前（上）の兄弟、なければ直後（下）の兄弟、どちらもなければ親とする。判定は `src/model/mindmap.ts` の `nodeToSelectAfterRemove` で行う。
- **経緯**: 「子ノードを delete で削除したとき、上の兄弟、なければ下の兄弟、なければ親にフォーカスさせたい」という要望による。それまでは常に親が選択されていた。
- **補足**: 「上」「下」は親の `children` の並び順で判断する。ルート直下の左右の振り分け（`side`）は考慮しない。

### D-15 フローティングノードと、ルートの座標移動

- **決定**:
  - 余白をダブルクリックすると、その位置にフローティングノード（親を持たない独立した根）を作る。フローティングノードからも子・孫を追加して別のツリーを作れる。
  - 座標を持つのはルート（メインのルートとフローティングノード）だけで、ドラッグで動かせる。子孫の位置は従来どおり自動レイアウトで決まる。
  - 通常のノードのドラッグは従来どおり「別の親への付け替え」。座標移動は根のドラッグにだけ割り当て、操作の衝突を避ける。
  - すべてのツリーを同じマップ（同じファイル）に保存する。XML は `mindmap` 直下に `node` を並べ、最初がメインのルート、2 つ目以降がフローティングノード。
  - 座標は XML の全ノードに `x / y`（ノード中心のマップ座標）として書き出す。読み込み時に位置として使うのは根の座標だけで、それ以外は自動レイアウトの結果を参考情報として残すもの。
- **経緯**: 「余白をダブルクリックしたときにフローティングノードを作り、そこから新たにツリーを作れるようにしたい。同一マップファイルに保存し、座標が分かるようにしたい。ノードごとの座標をドラッグ＆ドロップで動かせるようにしたい」という要望による。ドラッグ操作の割り当ては「ルートだけ座標移動」、座標の扱いは「XML に全ノードの座標を保存」を選んだ。
- **補足**:
  - 形式のバージョンは 1 のまま。従来のファイルはそのまま読み込める（古いアプリで新しいファイルを開くと、フローティングノードは無視される）。
  - 折りたたみで非表示になっているノードには座標が付かない。
  - 子ノードを自由な座標に置く手動配置は対象外（今後の候補）。

### D-16 Electron 版の自動アップデートに electron-updater を使う

- **決定**: `electron-updater` を実行時依存に加え、起動時に GitHub Releases の `latest.yml` を確認する。新しいバージョンがあればバックグラウンドでダウンロードし、次にアプリを終了するときにインストールする（`checkForUpdatesAndNotify` の既定の挙動。確認ダイアログは出さない）。
- **経緯**: 「electron-updater を導入したい。更新の通知は既定のままでよい」という要望による。リリースは D-13 のとおり GitHub Releases に公開しているため、そのまま更新元として使える。
- **補足**:
  - 対象は Windows（NSIS）のみ。コード署名はしていないので、更新時にも SmartScreen の警告が出ることがある。
  - パッケージ化していない起動（`dev:electron` / `start:electron`）では更新を確認しない。確認や取得に失敗してもログに残すだけでアプリは止めない。
  - `electron-updater` は `latest.yml` に書かれたファイル名で Release のアセットを探す。ファイル名にスペースがあると GitHub 側でピリオドに置き換えられて見つからなくなるため、`electron-builder.yml` の `win.artifactName` を `${productName}-Setup-${version}.${ext}` に固定した（v0.1.0 までのファイル名は `Mindmap.Setup.x.y.z.exe`）。
  - 自動アップデートの機能が入っているのは、この決定を含むバージョン以降。それ以前のバージョン（v0.1.0 まで）には更新機能が無いので、手動でインストールし直す必要がある。

## 2026-11-17

### D-17 マップ全体の PNG 書き出しは Canvas に直接描き、保存先は環境ごとに決める

- **決定**:
  - ツールバーに「画像書き出し」を追加し、マップ全体を PNG にする。既存の「書き出し」（XML）は残す。画像は XML のように読み込み直せないため、別のボタンにした。
  - 描画は DOM のキャプチャではなく、`computeLayout` が返す座標・接続線のパス・`bounds` を使って Canvas 2D に直接描く（`src/export/mapImage.ts`）。画像サイズは `bounds` に余白を足して決め、画面の表示状態に左右されないようにする。
  - 解像度は 2 倍を既定とし、Canvas の上限を超える巨大なマップでは倍率を自動で下げる（途切れた画像や描画失敗を避けるため）。
  - 配色は常にライトテーマ（白背景）にする。ダークモードの画面とは独立させ、共有や印刷でそのまま使えるようにする。
  - 保存先は、Electron 版では保存ダイアログで選ばせ、Web 版ではブラウザ標準のダウンロード（通常はダウンロードフォルダ）にする。
- **経緯**: 「書き出しボタンから現在のマインドマップ全体を PNG で出力したい。画像のサイズはマップ全体が収まるように可変にしたい」という要望と、続けての「Electron 版では保存先を選べるように、ブラウザ版ではデフォルトのダウンロードディレクトリに保存したい」という要望による。
- **補足**:
  - Electron の保存ダイアログは IPC（`export:saveImage`）でメインプロセスが開く（`electron/imageFiles.ts`）。Electron 本体に依存する部分（`dialog` など）は `main.ts` から引数で渡し、ファイル名の整形と書き込みは Node 環境でテストできるようにしている。
  - 当初は「書き出し」ボタンを PNG に置き換えるか迷ったが、XML の書き出し・読み込みは同じ形式でマップを受け渡す機能（D-07）なので残した。
  - ファイル名は、マップのタイトルではなく `mindmap-export-YYYYMMDDHHmmss.png`（ローカル時刻）にする。「保存時のファイル名はこの形式にしてほしい」という要望による。書き出しのたびに別名になるので上書きされず、タイトルに使えない文字が含まれる問題も起きない。
  - 一時 URL の解放（`revokeObjectURL`）は、ダウンロード開始前に無効になるのを避けるため遅延させている。

### D-18 パッケージマネージャーに pnpm を使う（2026-11-27）

- **決定**: 依存パッケージの管理を npm から pnpm に切り替える。`package-lock.json` は削除し、`pnpm-lock.yaml` を使う。readme・コマンド集のコマンドは `pnpm` 表記にする。
- **経緯**: 「pnpm を使う変更を用意している。readme に pnpm を使った環境構築の手順を追加してほしい」という依頼による。
- **補足**:
  - `package.json` の `package` スクリプト内部の `npm run build:electron` は変更していない（`pnpm package` からも動作する）。
  - pnpm 10 以降は依存のインストール後スクリプトを既定で実行せず、Electron 本体が取得されない。`package.json` の `pnpm.onlyBuiltDependencies` に `electron` と `esbuild` を指定して許可している。
  - リリース用ワークフロー（`.github/workflows/release.yml`）も `npm ci` から `pnpm install --frozen-lockfile` に変更した（`package-lock.json` を削除したため、そのままではタグ push 時のビルドが失敗する）。

### D-19 ノードのコンテンツとしてテーブルを持てるようにし、操作は右クリックメニューから行う（2026-11-27）

- **決定**:
  - `MindMapNode` に `table?: string[][]`（`rows[行][列]`）を追加し、これがあるノードを「テーブルノード」とする。テーブルノードは `text` を使わない（空文字）。ノードの種類を表す別フィールドは設けず、`table` の有無で判定する。
  - 右クリックメニュー（`ContextMenu`）を新設し、「子にテーブルを追加」と、テーブルノードの行・列の追加 / 削除をここから行う。行・列の操作は右クリックしたセルを基準にする。
  - 新しいテーブルは 2 行 × 2 列。最小は 1 行 1 列で、最後の行・列は削除できない。セルは 1 行のテキストのみで、見出し行やセルの結合は持たない。
  - テーブルにできるのはルート以外のノードのみ（ルートのテキストはマップのタイトルに使うため）。→ 変更（D-20: フローティングノードもテーブルにできる）
  - XML では `node` の最初の子要素に `table` / `row` / `cell` を置く。既存の読み込み処理は `node` 以外の子要素を無視するので、形式のバージョンは 1 のままにした。
  - 画面ではテーブルノードを深さに関わらず白地 + 枝の色の枠線で描く（深さ 1 の塗りつぶしのままだと表として読みにくいため）。PNG 書き出しも同じ見た目にする。
- **経緯**: 「右クリックのメニューからマインドマップの子にテーブルを追加できるようにしたい。テーブルを持つ要素を右クリックして、列や行の追加 / 削除ができるようにしたい」という要望による。
- **補足**:
  - これまで右クリックメニューは無かったため、テーブル以外の基本操作（子ノードの追加・削除）も同じメニューに入れた。
  - セルの編集はダブルクリック・メニューの「セルを編集」・`F2`（左上のセル）で始める。テーブルノード選択中の文字キーでは編集を始めない（入力先のセルが曖昧なため）。
  - セル編集中の blur が `Tab` による次のセルへの移動の後に届いても、別のセルを確定しないよう、確定時にセルの位置を照合している。

### D-20 余白の右クリックメニューからテーブルのフローティングノードを作れるようにする（2026-11-27）

- **決定**:
  - 余白（ノードの無い所）を右クリックしたときもメニューを開き、「フローティングノードを追加」と「テーブルを追加」を出す。どちらも右クリックした位置を中心に作る。
  - 「テーブルを追加」では、フローティングノード**そのもの**をテーブルノードにする（見出しのノード + 子のテーブル、という形にはしない）。
  - これに伴い D-19 の「テーブルにできるのはルート以外」を、「メインのルート以外」に改める。メインのルートはマップのタイトルに使うので、引き続きテーブルにしない。
  - フローティングのテーブルは枝の色を持たないので、枠線はルートの色にする。ダークモードでは背景に埋もれるため、CSS 変数 `--root-table-color` で明るい灰色に切り替える。
- **経緯**: 「何もないエリアで右クリックした際はフローティングノード内にテーブルを追加したい」という要望による。形について「フローティング自体をテーブルにする」か「見出し + 子にテーブル」かを確認し、前者を選んでもらった。メニューにはテキストのフローティングノード追加も入れることにした（ダブルクリックと同じ操作をメニューからもできるようにするため）。

### D-21 ノードとテーブルのセルのテキストを Shift+Enter で複数行にする（2026-11-27）

- **決定**:
  - 子孫ノード・フローティングノード・テーブルのセルの編集中に `Shift+Enter` で改行できるようにする。`Enter` は従来どおり確定。
  - メインのルートは 1 行のまま（マップのタイトル・一覧の表示に使うため）。`Shift+Enter` を押しても何もしない。→ 変更（D-22: メインのルートも複数行にできる）
  - 改行はテキスト中の改行文字（LF）としてそのまま持つ（データ型は変えない）。XML の `node@text` は従来から `&#10;` でエスケープしていたため形式は変わらない。セルの内容も `&#10;` で書き出し、1 つの `row` 要素が XML 上で 1 行に収まるようにする。
  - レイアウトは行数で高さを、一番長い行で幅を決める。テーブルは行ごとに、一番行数の多いセルに合わせて高さを変える（`TableLayout.rowHeight` を `rowHeights` に変更）。
  - 編集欄は `input` から `textarea` に変える。行の高さ（line-height）は `layout.ts` の値を inline style で渡し、計算と表示を一致させる。
- **経緯**: 「spec.md の未実装にある複数行テキストに対応したい。フローティングノード・子要素で Shift+Enter を押したら改行したい。テーブルのセルでも同様にしたい」という要望による。対象に挙がらなかったメインのルートは 1 行のままにした。

### D-22 メインのルート（中心トピック）も複数行にでき、タイトルは行を空白でつないだものにする（2026-11-27）

- **決定**:
  - D-21 で 1 行に限っていたメインのルートも、`Shift+Enter` で改行できるようにする。これですべてのノードとセルで同じ操作になる。
  - マップのタイトル（`titleOf`）は、ルートのテキストを行に分け、各行の前後の空白を除き、空行を除いて空白 1 つでつないだものにする。マップ一覧の表示や XML 書き出しのファイル名に改行が入らないようにするため。
- **経緯**: 「中心トピックも Shift+Enter で複数行にできるようにしたい」という要望による。
- **補足**: 保存済みのファイルのタイトルも読み込み時に `titleOf` で作り直すため、既存のマップへの影響は無い（従来の 1 行のタイトルはそのまま）。

### D-23 開いているマップ内のテキスト検索を Ctrl+F のポップアップで行う（2026-11-27）

- **決定**:
  - `Ctrl+F` で画面左上（ツールバーの下）に検索欄を浮かせて表示する。ブラウザ標準のページ内検索の代わりにする（Electron 版にはページ内検索が無く、Web 版でもパン・ズームしたキャンバスでは使いにくいため）。
  - 検索結果はノード単位にする。テーブルノードはセル単位にせず、いずれかのセルが一致すれば 1 件として数える（ジャンプ先は「要素」なので、ノード単位が分かりやすいため）。
  - 一致部分は黄色（`mark`）でハイライトする。表示中の結果は濃い黄色で区別する。
  - `Enter` / `Shift+Enter` と ↑↓ ボタンで結果を順に切り替え、端では反対の端に戻る。
  - `Esc`・マップの何も無い所のクリック・×ボタンで検索を終える。検索語は残さない。
  - 折りたたまれた部分の中の結果にジャンプするときは祖先を展開する。データ（`collapsed`）の変更になるので Undo の対象になる。隠れたノードを検索対象から外すよりも、見つけられる方を優先した。
  - 大文字・小文字は区別せず、正規表現は使わない（入力した文字そのものを探す）。
- **経緯**: 「開いているマップ上のテキストを検索し、ヒットしたらその要素にジャンプしたい。ヒットした部分はイエローでハイライトしたい。複数件のときは次の結果に切り替えたい。Ctrl+F で画面左上にポップアップを出し、Esc や何も無い所のクリックで検索を終えたい」という要望による。

### D-24 ドラッグ＆ドロップでの兄弟の並び替えと、ルートの左右の入れ替え（2026-11-27）

- **決定**:
  - ノードのドラッグ＆ドロップで、ドロップ先のノードのどこに落としたかによって置き方を変える。上端・下端から高さの 30% の範囲なら前・後ろの兄弟として、中央付近なら従来どおり子として置く。
  - ルートへのドロップは常に子として置き、ルートの左半分なら左側、右半分なら右側に置く。ルート直下のノードの前後に置いた場合は、そのノードと同じ側にする。これで左右の入れ替えを専用の操作を増やさずに行える。
  - これまで無効にしていた「現在の親へのドロップ」は、並びや側が変わる場合（末尾への移動、ルートの反対側への移動）は有効にする。並びも側も変わらないドロップだけを無効にし、`moveNodeTo` が同じ参照を返すかどうかで判定する。
  - 兄弟として入る位置は緑の線、子として入るノードは緑の枠で示す。
- **経緯**: 「要素の前後関係や左右を変更したい。兄弟要素をドラッグ＆ドロップで並び替えたい。中心ノードの右から左、左から右に要素を移動したい」という要望による。
- **補足**: キーボードでの並び替えは今回は入れていない（未実装の候補に記載）。

### D-25 main への PR と push で GitHub Actions の CI を実行する（2026-11-27）

- **決定**:
  - `.github/workflows/ci.yml` を追加し、`main` への PR と `main` への push（PR のマージ）をきっかけに、lint（oxlint）・型チェック（`tsc -b`）・テスト（Vitest）・Web 版と Electron 版のビルドを実行する。
  - 実行環境は Ubuntu（Windows より起動が速いため）。Node 24・pnpm 10 はリリース用ワークフローに合わせる。
  - インストーラの作成は含めない（リリース時だけでよく、時間もかかるため）。Electron 本体のダウンロードも `ELECTRON_SKIP_BINARY_DOWNLOAD` で省く。
  - 1 つのジョブで順に実行する。依存のインストールを 1 回で済ませるため。
  - 同じ PR の古い実行は `concurrency` で取り消す。権限は `contents: read` のみ。
- **経緯**: 「GitHub Actions で main への PR と main への merge をトリガーに確認できるようにしたい」という要望による。
- **補足**: CI の失敗で PR のマージを止めるには、GitHub のリポジトリ設定でブランチ保護（必須ステータスチェックに `CI / check` を指定）を行う必要がある。設定はリポジトリ側の操作なので、このワークフローには含めていない。
